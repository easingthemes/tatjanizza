# Contributing

Notes for working on the code. If you only want to change words or images on the site, you don't
need any of this — see [docs/editing-content.md](./docs/editing-content.md) instead.

## Setup

Node 22 (`.nvmrc`) and pnpm.

```bash
nvm use          # or otherwise get onto Node 22
pnpm install
cp .env.example .env
pnpm dev
```

`.env` needs `NEXT_PUBLIC_TINA_CLIENT_ID`, `TINA_TOKEN` and `NEXT_PUBLIC_TINA_BRANCH` from
[TinaCloud](https://app.tina.io). Without them `pnpm dev` still runs, but visual editing and the
hosted content API won't work.

## Commands

| Command | |
|---|---|
| `pnpm dev` | Tina GraphQL server on `:4001` + Next dev on `:3000` |
| `pnpm build` | `tinacms build` then `next build` — needs valid TinaCloud credentials |
| `pnpm build-local` | build against local files, skipping cloud checks |
| `pnpm lint` | Biome |
| `npx tsc --noEmit` | typecheck |

## Before you commit

**There is no test suite.** Verification is manual, so actually do these:

1. `npx tsc --noEmit` — clean
2. `pnpm lint` — clean
3. Load the affected route in the browser and look at it
4. If you touched anything editable, open `/admin` and confirm click-to-edit still selects the right
   fields

Biome's config is non-obvious in a couple of places: single quotes, single-quoted JSX attributes,
2-space indent, **160-character lines**, semicolons always. `noExplicitAny` and `noUnusedVariables`
are deliberately off, so unused imports won't fail the build.

## Committing

**Check before you push.** There is no CI, so nothing catches a broken build except you:

```bash
./scripts/preflight.sh   # 0 = safe to push, 2 = partial check, 1 = do not push
```

It installs, lints and runs the same build Vercel runs. The full build needs the three TinaCloud
vars in your environment (`.env` is enough); without them the script still validates the Tina schema
and exits 2 — useful, but not a complete check.

**`main` deploys straight to production.** There's no staging environment and no CI gate — a push to
`main` is a live deploy to www.tatjanizza.com. For anything non-trivial, branch and let Vercel build
a preview first:

```bash
git switch -c short-description
# ... work ...
git push -u origin short-description
```

Commit messages: a `type: summary` first line (`feat:`, `fix:`, `docs:`, `chore:`), then a body
explaining *why* if it isn't obvious. Keep unrelated changes in separate commits.

### Previews

Every branch pushed to the repo gets its own preview deployment, built automatically. The build
takes roughly **one to three minutes** after the push — until it finishes, the URL 404s or still
serves the previous commit.

The stable per-branch URL is:

```
https://tatjanizza-git-<branch>-kaidx.vercel.app
```

where `<branch>` is the branch name with every `/` and other non-alphanumeric character replaced by
`-` (so `claude/my-fix` becomes `claude-my-fix`). Long branch names are truncated and get a short
hash appended instead, so if the URL doesn't resolve, take the exact link from the Vercel deployment
check on the commit, or from the project dashboard — `tatjanizza` in the Vercel team **kaidx**
(*vebkurs-5678's projects*).

Preview deployments are **public**: anyone with the link can open them, no Vercel account or login
needed. Handy for sending work in progress to Tatjana for review, but treat any preview link as
public — don't put anything on a branch you wouldn't publish. (`/admin` is the exception; it still
needs a TinaCloud login.)

## Architecture in one minute

Fuller notes live in [CLAUDE.md](./CLAUDE.md). The essentials:

Content is **files, not a database** — Markdown/MDX/JSON under `content/`, read through Tina's
generated GraphQL client at `@/tina/__generated__/client` (default export; note it is *not*
`@/tina/client`).

Every route is a **server/client pair**:

- `page.tsx` — server component. Fetches with `await client.queries.X()`, wraps in `<Layout>`,
  spreads the result into the client component, and exports `generateStaticParams()`.
- `client-page.tsx` — `'use client'`. Calls `useTina({ query, data, variables })` and renders.

`useTina` returns only `data` — no loading or error state — so all error handling (`notFound()`)
belongs in the server component.

### Never edit `tina/__generated__/`

It's regenerated by `tinacms dev` / `tinacms build`. **Restart `pnpm dev` after changing any schema**
or the generated types and client will be stale and you'll chase phantom type errors.

### Editable elements need `tinaField`

Anything an editor should be able to click needs `data-tina-field={tinaField(parentObject, 'fieldName')}`.
Pass the parent object and a field name — never a string literal, never a computed value. Omitting it
doesn't break the build; it just silently makes that element uneditable in the CMS.

## Adding a content block

Blocks are the sections that make up a page. `content/pages/*.mdx` holds a `blocks` array, and
`components/blocks/index.tsx` switches on `block.__typename` to pick a component. Adding one means
touching exactly three places:

1. **Create `components/blocks/<name>.tsx`**, exporting *both* the component and its Tina schema
   from the same file — e.g. `export const heroBlockSchema: Template`. Include
   `sectionBlockSchemaField as any` in `fields` to get the shared background option.
2. **Register the schema** in `tina/collection/page.ts` under `templates`.
3. **Add a `case`** to the `Block` switch in `components/blocks/index.tsx`.

Schema co-location is the convention that matters here: Tina schemas import from `components/`, not
the other way round. The files in `tina/collection/` stay thin.

Then restart `pnpm dev` so the types regenerate.

## Adding a collection

New content *type* (as opposed to a new section) means a new file in `tina/collection/`, registered
in `tina/config.tsx` under `schema.collections`. Give it a `ui.router` so Tina knows what URL a
document maps to, then add matching routes under `app/`. Copy the shape of an existing pair —
`tina/collection/post.tsx` with `app/posts/` is the closest example.

## Rich text

`components/mdx-components.tsx` exports one `components` object passed to every `<TinaMarkdown>`.
A new custom MDX component needs an entry there **and** a `templates` entry on the `rich-text` field
in the collection schema. Only doing one of the two is the usual mistake.

## Styling

Tailwind v4, configured entirely in `styles.css` via `@theme inline` and CSS custom properties in
oklch. **There is no `tailwind.config.js`** — don't create one. shadcn/ui is set up in
`components.json` (new-york style, lucide icons); generated primitives go in `components/ui/`.

## Restoring the real site

The site currently shows a temporary coming-soon splash. To bring back the real home page, reverse
three things:

1. `app/page.tsx` — delete the `<ComingSoon />` render, uncomment the Tina-driven `Home` below it
   (including `export const revalidate = 300`)
2. `components/layout/layout.tsx` — uncomment the `Header`/`Footer` imports and their JSX, and put
   `pt-20` back on `<main>` (it clears the fixed header)
3. Delete `components/coming-soon.tsx`

Two translations in that component's `PHRASES` array are marked `UNVERIFIED` (Akkadian, Phoenician)
and several others are best-effort. They need Tatjana's review before anyone treats them as correct.

## Gotchas worth knowing

- **Favicons must be RGBA.** `app/favicon.ico` is generated from her artwork; if you regenerate it,
  convert to RGBA first. An RGB `.ico` makes Turbopack fail with *"The PNG is not in RGBA format"*
  and returns a 500 on every route.
- **`metadataBase`** is hardcoded to `https://www.tatjanizza.com` in `app/layout.tsx`. OpenGraph
  image paths resolve against it, so it must change if the production domain does.
- **Images** — remote hosts must be allowlisted in `next.config.ts`; `assets.tina.io` and
  `res.cloudinary.com` already are.
- **`.github/copilot-instructions.md`** is inherited from the starter. It's broadly right about Tina
  patterns but its file paths (`src/`, `@/tina/client`, `utils/tina-client.ts`) don't match this
  repo. Trust the actual code.
